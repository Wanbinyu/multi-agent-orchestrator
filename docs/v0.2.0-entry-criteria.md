## P0 Audit Conclusion

On 2026-07-21, P0 audit covered five classes: secret handling, out-of-bounds write, false task completion, plugin/tool privilege escalation, and command execution.

**Found 1 P0, fixed**:

- `run_command` (`src/tools/worker_tools.py`) allowed interpreter inline code execution via `python -c` / `node -e` / `node --eval` / `node -p` / `node --print`. Prefix allowlist (`"python "`, `"node "`) passed these commands with no inline-code flag check (`frontend_smoke.py` and `benchmark.py` already had similar checks but they were not wired into `run_command`). A model, via prompt injection or hallucination, could issue `python -c "import os; os.system(...)"` to read `.env` (secret leak), write out of bounds (bypass `permission_rules`), make network requests, or destroy data; under `auto` mode this runs without confirmation.
- **Fix**: `run_command` preflight adds `_has_inline_interpreter_code`, which returns `inline_interpreter_code` and refuses for `python -c` (only when no `-m`, to avoid false-rejecting `python -m pytest -c config`) and `node -e/--eval/-p/--print`. Tests added/updated for rejection, module mode not false-rejected, and script files not false-rejected.
- **Impact**: `run_command` in `v0.1.0-beta.6` and earlier is affected; `readonly` sessions are not ( `run_command` category is `execute`; readonly denies it outright).

**Other four classes SOUND**: secrets only in `.env`; `providers.yaml` stores only `${VAR}` references; errors/diagnostics redacted (exception type only); file tools use `resolve_path` ownership constraints + `permission_rules` deny>ask>allow + Worker write isolation so Workers cannot escalate via task splitting; `CompletionAudit` is pure deterministic and model body text cannot override; `AdversarialTester`/`Reviewer` cannot promote failure to completion; plugin-registered tools go through the same `permission_rules.decide` and do not bypass the permission layer (same-process privileges of Python plugins are by design, not P0).
